**Serving both words from one plugin is the point.** `distro:` is the build vocabulary a box declares; `os:` is the operating system a source names (`D-SRC-2`). They share every inner shape — a `bootstrap:` or `format:` block means the same thing on both — and differ only in what an os must say about itself. **Two plugins would have made two vocabularies of one.**

```cue
#OsInput: {
	description!: family!: package_manager!: init!: boot?:        // the five that make it an OS
	inherit?: inherit_package?: bootstrap?: workaround?: format?:
	base_user?: bootstrapper?: bootloader?: disk_layout?: installer?:
}
```

## The parity test caught real drift, on its first run

**`#OsInput` mirrors spec's `#Os`, NOT this plugin's `#DistroInput`** — and I found that out by being wrong:

```console

    #OsInput does not mirror spec's #Os field "inherit"
    #OsInput does not mirror spec's #Os field "inherit_package"
```

**The legacy build vocabulary spells three concepts differently:** `inherits` / `inherit_packages` against the contract's `inherit` / `inherit_package`, and three flattened bootstrappers (`pacstrap`, `debootstrap`, `alpine_bootstrap`) against the contract's one grouped `#OsBootstrapper`.

**A gate that mirrored the legacy names would accept authored bodies core then rejects** — the exact drift `schema_parity_test.go`'s header records happening three times before (`installer`, `disk_layout`, `present_template`). **Those three spellings are the R2 debt [`opencharly/opencharly#1200`](https://github.com/opencharly/opencharly/issues/1200) records, now measured rather than assumed.**

### The fifth commit: four inner defs that had no guard at all

**`TestOsOnlyInnerDefsMatchSpec` guards `#OsInput`'s FOUR own inner defs** — `#OsPackageManager`, `#OsInit`, `#OsBoot`, `#OsBootstrapper`. **The mirrored sweep never reached them**: `TestEveryMirroredDefMatchesSpec` follows the `#Ds` + spec-name convention, and these carry this file's own names.

**Writing it exposed four blind spots in the shared helper it could not reuse**, each fixed here:

| helper | blind spot | consequence |
|---|---|---|
| `topLevelFields` | matches only `key?:` | a REQUIRED field (`container!:`) extracted as nothing |
| `defBody` | matches names as SUBSTRINGS | `#Os` matched inside `#OsInit` — compared two unrelated field lists |
| `topLevelFields` again | a ONE-LINE def has no indented lines | `#Boot: {firmware: …, kernel?: …}` extracted as nothing, and **zero-vs-zero PASSES** |
| — | a brace read stops at the first inner `}` | spec's `_packageManager: {dnf: {}, apt: {}}` returned only `dnf` |

**Two helpers carry the fix:** `defFields` (brace-aware, attribute-aware, one-line-aware, exact-key) and `declLine` (a definition's declaration line, for vocabularies and one-liners).

**`#OsInit` is compared against `_initRole`'s ROWS**, not against spec's `#OsInit` — spec's is a comprehension over that table and has no static fields, so a field-for-field comparison would be zero-versus-two and prove nothing.

**Proven red:** deleting `kernel?` from `#OsBoot` fails the guard; restoring it passes.

### The outer comparison had the same blind spot, and I only fixed the inner one

**`TestOsInputAddsExactlyOsFields` read both sides with `topLevelFields`** — the very helper whose `key!:` blind spot I documented in `defFields`'s comment. So `description!`, `family!`, `package_manager!` and `init!` extracted as **nothing on both sides**, and the comparison was **zero-versus-zero on the four fields D-CANDY-3 and D-SRC-2 care most about.**

**Deleting `init!` from `#OsInput` failed no test at all.**

**Proven red, all four** — deleting `description!`, `family!`, `package_manager!`, or `init!` each fails `TestOsInputAddsExactlyOsFields`. Before this commit, none of them failed anything.

## The `OpLoad` arm, and why it is not optional

**The host dispatches kind-blindly, so the word arrives on the request** (`req.GetReserved()`), not from the plugin. Decoding an `os:` body into `spec.Distro` would **silently drop its five extra fields and hand the host back a body it had just validated as complete** — a canonicalisation that loses data rather than canonicalising it.

**`OpResolve` is word-aware too, and REFUSES rather than truncating.** Advertising the `os` word to a kind-blind host means an `os` request can reach `OpResolve`, whose input type carries none of the five os-only fields — so resolving it would build a `ResolvedDistro` from a truncated body, **the same defect the `OpLoad` arm prevents, one operation over.** It now refuses any word but `distro`, by name. **An error is the honest answer while `os` resolution is unimplemented**: it makes a misroute loud at the boundary instead of shipping a wrong resolved distro into a build. When `os` resolution is designed it gets its own arm, not a fallthrough — and `TestInvokeResolveRefusesTheOsWord` fails if the guard is removed.

**Both words share ONE body.** The first draft copy-pasted the `distro` arm's unmarshal/marshal/error-prefix block and changed the type; it is now `opLoadCanonical[T](word, req)`. **Two copies of a canonicalisation is how two words of one vocabulary quietly acquire two canonical forms** — the drift the parity tests exist to catch, arriving through the mechanism meant to prevent it. The word is threaded through for the error prefix, so a failure still names its kind.
