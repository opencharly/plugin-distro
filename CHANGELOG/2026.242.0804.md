# 2026.242.0804 — fix(schema): #DistroInput had drifted behind spec's #Distro

## Summary

This plugin serves `kind: distro` and validates an authored `distro:` body against its
**own** self-contained `#DistroInput` before dispatching. That duplication is sanctioned —
the plugin schema must compile standalone while spec's `#Distro` must generate Go — but it
means the two can **drift**, and when they do the failure is actively misleading: charly's
core accepts a field and this plugin rejects it with

```
#DistroInput.disk_layout: field not allowed
```

which reads like the field does not exist anywhere.

Two fields were missing:

| Field | Added to spec in | Consequence of the gap |
|---|---|---|
| `installer` | [spec#71](https://github.com/opencharly/spec/pull/71) | **already drifted** — an authored `installer:` block has been rejected here since that landed |
| `disk_layout` | [spec#72](https://github.com/opencharly/spec/pull/72) | surfaced this: a charly build carrying an omarchy distro entity failed to validate |

### Every file in the diff

| File | What changed |
|---|---|
| `candy/plugin-distro/schema/distro.cue` | `#DsDiskLayout`, `#DsSubvolume`, `#DsInstaller`, `#DsInstallerFile` added; `disk_layout?` and `installer?` wired into `#DistroInput` |
| `candy/plugin-distro/schema_parity_test.go` | **new** — the drift guard and a dangling-reference guard |

### How this stops recurring

The parity test compares `#DistroInput`'s **top-level field set** against the set spec's
`#Distro` authorises, so the next omission fails *here, next to the fix* rather than in a
consumer's build log.

Inner defs are deliberately **not** compared: they differ in name (`#DsBootloader` vs
`#Bootloader`) and carry no `@go` annotations, so comparing them would be noise. What
matters is that every field a distro entity can author is authorable here.

The `want` list is a literal rather than something read from the `spec` module. Importing
spec to check the standalone schema would defeat the property being checked — this def
exists precisely so the plugin compiles without it.

## How tested

```
$ go test -count=1 ./...
ok  	github.com/opencharly/plugin-distro/candy/plugin-distro	0.005s
?   	github.com/opencharly/plugin-distro/candy/plugin-distro/cmd/serve	[no test files]
?   	github.com/opencharly/plugin-distro/candy/plugin-distro/params	[no test files]
```

**The guard was verified to discriminate, not merely to pass.** Deleting the `disk_layout`
line reproduces the exact failure this PR fixes, with a readable diff:

```
$ python3 -c "…remove the disk_layout line…"
$ go test -count=1 -run TestDistroInputCovers ./...
--- FAIL: TestDistroInputCoversEverySpecDistroField (0.00s)
    schema_parity_test.go:44: #DistroInput fields drifted from spec's #Distro.
         got: [alpine_bootstrap base_user bootloader bootstrap debootstrap dnf format inherit_packages inherits installer pacstrap version workaround]
        want: [alpine_bootstrap base_user bootloader bootstrap debootstrap disk_layout dnf format inherit_packages inherits installer pacstrap version workaround]
```

The line was then restored and the suite re-run green. A test that cannot fail is not a
gate, and this one was made to fail on purpose before being trusted.

The originating symptom is also reproducible: `charly box validate` in the charly repo,
with an omarchy distro entity carrying `disk_layout:`, reported

```
node "omarchy": plugin kind:distro: plugin_input fails #DistroInput:
#DistroInput.disk_layout: field not allowed
```

which is what sent me here.
