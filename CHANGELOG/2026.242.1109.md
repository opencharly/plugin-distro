## The generated params had drifted, and that is in here too

Regenerating removes the two dead fields — and surfaced that the committed `params/cue_types_gen.go` no longer matched its own schema. It was missing fields the schema already declares:

```
+	Disk_layout DsDiskLayout `yaml:"disk_layout,omitempty" json:"disk_layout,omitempty"`
+	Installer   DsInstaller  `yaml:"installer,omitempty"   json:"installer,omitempty"`
	(plus a further block at the end of the file)
```

So the diff is the two dead fields going out **plus the generated projection catching up with its source**. Both belong in the same change: a generated file that does not match its schema is not a smaller problem than the dead fields that prompted looking at it, and splitting them would leave a "DO NOT EDIT" file knowingly wrong.

## How tested

Regenerated, never hand-edited — the same pipeline `spec`'s `task cue:gen` runs, with the pinned cue (`v0.16.1`) built by spec's `bootstrap-cue`:

```
1. cue exp gengotypes over schema/distro.cue, headed `package params` + @go(params)
2. spec's schemagen -mode=retag   # doubles the json tags with yaml tags
3. gofmt
```

Step 2 matters: a bare `gengotypes` run emits `json:"…"` only, and this repo's committed file carries both tags. Diffing before the retag showed exactly that difference, which is how I know the pipeline is the right one rather than a plausible-looking approximation.

## Ordering

Last of three, and the order was forced: removing a schema declaration before the authored usage would reject a `charly.yml` that still writes the field. Authored usage first (charly#484, merged), then `spec` (#77), then this. At no point was an authored field rejected by the schema, and no live consumer was ever left without its field — there were none.
