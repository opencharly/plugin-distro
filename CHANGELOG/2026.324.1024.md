# 2026.324.1024 — fix(distro): declare the os and source providers, or the kinds are unparseable

## Summary

**A kind has TWO declarations, and #16/#18 made only one.** This adds the second.

| declaration | what it makes the kind | where |
|---|---|---|
| `NewMeta`'s `{Class:"kind", Word:"os", InputDef:"#OsInput"}` | **SERVABLE** — the provider handles it | `plugin.go` — done in #16 |
| the candy's `plugin: providers: [- kind:os]` | **AUTHORABLE** — the parser recognises it | **this PR** |

**`charly/plugin_prescan.go:725` reads this list into `declaredKind`, which becomes `spec.Threaded.Kinds`** — and that is the **only** recognition path, because `spec.KindWords` is empty now that every kind is plugin-served:

```go
// spec/vocab_gen.go:10
var KindWords = []string{}

// loaderkit/parse.go:78 — classifyKind
if kindWordSet[k] || stepKeywordSet[k] { return kindWordSet[k] }   // EMPTY
if t.Kinds[k] { return true }                                       // ← the only path
```

**So the merged capability was inert at the one place it mattered.** An authored `os:` or `source:` node was rejected at parse time:

```console
$ charly box validate
charly: error: node "arch-os": no kind discriminator — none of its keys ("os") is a recognized kind
```

**The manifest declared only `- kind:distro`.**

## Why the tests in #16/#18 could not see this

**They call `Invoke` and `Describe`.** The gap is in the **parser**, which neither touches — and `Describe` is the check I added *specifically* to prove the registration, which makes this the more instructive miss: **I tested the registry I knew about and not the second registry that actually gates authored input.**

`TestNewMetaAdvertisesBothVocabularyWords` asserts the word reaches `Describe`. It cannot assert the word reaches `declaredKind`, because `declaredKind` is populated from the manifest by a different mechanism.

**The `source:` half is NOT proven, and cannot be, for a reason that is not this PR's:** [`opencharly/opencharly#1203`](https://github.com/opencharly/opencharly/issues/1203) — `os` is both a kind word and `#SourceFields.os`, so a source naming its os has the reference read as a discriminator (`node "os": expected a mapping value, got yaml kind 8`). **Filed, with three resolutions and the note that the two colliding spellings are both in `DESIGN.cue`.**

### The fresh rebuild, which `box validate` performs here

**This candy's `plugin:` block names `source: github.com/opencharly/plugin-distro/candy/plugin-distro`** — the plugin at this tree's own path. So `charly box validate` cannot use a cached provider for it: it **builds the plugin from this working tree** and reports the build it served:

**The `served from …/plugin-build/views/…` line with a content-addressed `sha256` IS the rebuild record** — a changed plugin produces a changed view hash, and the hash moved when this PR's manifest changed (`ff91847bb10c8a74` → `b46759d1e11204c3`). **There is no separate `charly update` step to run:** a plugin candy has no deployable image, so `box validate`'s source build is the whole gate this change class has.

**A separate, ALREADY-FILED defect is not fixed here, and it is the more serious one.** A freshly built `charly` binary contains `#DistroInput` but **not** `#OsInput`/`#SourceInput`, even though `bootstrap-charly.sh` logs `Downloading github.com/opencharly/plugin-distro:HEAD`:

**A merged plugin can be silently absent from the binary that claims to have compiled it.** That is [`opencharly/charly#715`](https://github.com/opencharly/charly/issues/715) — *"a pin that does not pin — a cold repo cache silently serves the umbrella-view tag instead of the pinned ref"* — with [`#1019`](https://github.com/opencharly/charly/issues/1019) covering the same class at the `box validate` seam. **No new issue is filed because both already describe it precisely**, and this PR cannot verify a fix for it: the binary available here cannot be made to contain the merge.
