# 2026.242.1131 — fix(resolve): carry disk_layout and installer — both were silently dropped

## Summary

`resolveDistro` is a hand-written field copy, and it **forgot two fields**: `disk_layout`
and `installer`.

Everything else accepted them. spec's `#Distro` declares both. This plugin's own
`#DistroInput` accepts both (added in #4). `charly box validate` passes on a distro
authoring them without a word. Then this function does not carry them across, and every
consumer receives `nil`.

**Nothing errors.** The consumer just takes its default path.

### The btrfs subvolume feature does nothing

This is the cost, and it is already merged and shipped:

| PR | What it added |
|---|---|
| spec#72 | `#DiskLayout` + `#Subvolume`, on `#Distro` **and** `#ResolvedDistro` |
| plugin-vm#6, #7 | `EmitDiskBuildScript` builds subvolumes; the ESP mount point comes from the distro |
| charly#476 | omarchy authors `@`/`@home`/`@log`/`@pkg` and the ESP at `/boot` |

All four merged green. **All four are inert.** `DistroDef` *is* `spec.ResolvedDistro`
(`sdk/vmshared/spec_aliases.go:44`), and this copy never populated `DiskLayout` — so
`DiskLayoutFromDistro` has been receiving a nil layout and every distro declaring
subvolumes has silently been getting the historical bare-filesystem layout with the ESP at
`/boot/efi`.

The `installer` drop is the same shape and blocks `source.kind: iso` outright: an iso VM
cannot render its answers volume without the distro's `installer:` block, so
`charly vm build` fails with

```
distro "omarchy" declares no installer: block in the embedded build vocabulary
```

against a distro that plainly declares one.

**Found by running a real `charly vm build` against an authored `omarchy-vm` entity, not by
reading.** Both drops were invisible to every gate in the chain.

## Why the existing parity test could not catch this

`schema_parity_test.go` (from #4) compares the **served schema** against spec. That catches
"charly accepts a field and this plugin rejects it with `field not allowed`" — a loud
failure with a confusing message.

This is the strictly worse seam: **everything accepts the field**, it validates cleanly,
and the resolver quietly forgets it. A schema guard cannot see it, because the schema is
correct.

So `resolve_parity_test.go` is a second guard over a different seam — the resolver:

- author **every** field `spec.ResolvedDistro` declares, resolve, and fail on any that
  arrives zero. The failure names the fields and says to add them to the struct literal
  (and to justify in place, not delete the test, if one genuinely must not be carried).
- a companion test asserts the two fields **by value**, so a refactor cannot satisfy the
  first guard with a wrong value. It includes that installer template bodies arrive
  **unrendered** — rendering happens later against the vm entity's data, and a resolver
  that touched them would break every seed.

Adding a field to the schema is exactly the moment someone forgets the resolver, which is
why the two guards belong side by side.

## The spec bump

`v0.2026232.521-…` to **`v0.2026242.942`** — the first published version whose
`ResolvedDistro` carries both fields. Without it the two new lines do not compile
(`unknown field DiskLayout in struct literal`), which is itself a small piece of evidence
that this plugin had never been rebuilt against the spec that introduced them.
