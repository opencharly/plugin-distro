# 2026.276.1457 — feat(plugin-distro)!: mirror spec's present_template + derive the schema-parity guard from spec (charly#771)

## Summary

This plugin serves `kind: distro`, and it validates an authored `distro:` body against its **own, self-contained** `#DistroInput` (with inner `#Ds*` defs) before dispatching. That duplication is sanctioned — the plugin schema must compile standalone while spec's `#Distro` must generate Go — but the two can drift, and when they do the failure is confusing: charly core accepts a field and this plugin rejects it with `#DistroInput.<field>: field not allowed`, which reads like the field does not exist at all.

**That is what happened to `present_template`.** spec's `#Format` gained it (spec leg 1 of `opencharly/charly#771`, merged and tagged `v0.2026276.1337`), and this mirror did not, so an authored `present_template` — the command whose stdout lists the already-present packages, which leg 1/leg 2 use to subtract the venue's pre-existing packages from teardown — was rejected **here**, at the kind provider.

Two things are fixed, and the second is the one that matters:

**1. The mirror is completed.** One line in the inner `#DsFormat`, placed exactly where spec's `#Format` has it (immediately after `uninstall_template`), plus the regenerated `params/cue_types_gen.go` through this repo's own pipeline.

**2. The parity guard is replaced with a derived, inner-deep one.** The old guard compared **top-level fields only** — by explicit design — against a **hand-maintained literal**. `present_template` lives on the *inner* `#DsFormat`, one level below that guard, so it drifted **silently**. The file's own comments already recorded the identical class twice: `#Distro.installer` was "rejected here for months", and `disk_layout` was next. So the guard now reads spec's **own CUE source** — the embed in the spec module this plugin already requires — and descends into **every** mirrored def.

Measured on this head: **19** mirrored `#Ds*` defs plus `#DistroInput` all compare equal to spec.

**Why derived rather than a better literal.** A hand-maintained list has *two* drift surfaces — the schema, and the list — and re-checks only what someone remembered to write. The org's own precedent for a parity test is derived: `plugin-box/candy/plugin-box/validate_parity_test.go` asserts its closed set against `spec.ProviderClasses` and says so — *"DERIVED from spec.ProviderClasses (the ONE CUE-owned vocabulary)"*. Following that precedent is R3; keeping both would be two implementations of one invariant. The old test's rationale — *"Kept as a literal rather than read from the spec module because the plugin's schema is deliberately standalone — importing spec here to check standalone-ness would defeat the point"* — reasons about the **schema's** standalone-ness, which a **test** reading a dependency's CUE does not touch. It is deleted (R5).

**No new module dependency.** `github.com/opencharly/spec/schema` (`var FS embed.FS`) and `github.com/opencharly/spec/schemaconcat` (`ConcatSchema`) are subpackages of a module this plugin already requires; `schema` holds exactly one non-test Go file (the embed).

**No production Go changes.** The projection carries the whole format map by reference (`resolve.go:32` — `Format: d.Format`), so a new field on `spec.Format` flows through once the pin moves. `resolve.go`, `plugin.go` and `cmd/` are untouched.

Refs opencharly/charly#771 — this is the schema-mirror leg; the issue closes with the charly leg, not here.
